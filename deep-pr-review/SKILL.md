# deep-pr-review

GitHub の Pull Request を、通常の `/review` 単体より **多角度かつ高精度** にレビューする。
3 つの観点（標準 PR レビュー / 外部ハーネス独立レビュー / アーキテクト観点メタ検証）を重ね、最終的に
**重複排除・再ランクした統合レビュー1本** を **正しく分かりやすい日本語** で出力する。

本スキルは **TUI 専用**である — 外部ハーネス（codex / cursor-agent / agy / grok 等）を tui-harness の
ペインで起用する。実行可否の判定（どの TUI マルチプレクサが検証済みか）は tui-harness の
`mux.sh detect` に委ね、中止規定の正本はフェーズ0の TUI 専用ゲート。
前提スキル: tui-harness（agent-skills リポジトリ・必須）/ plainify（agent-skills リポジトリ・必須）。
PR へのコメント投稿は本スキルの責務外である（同一リポジトリの別スキル pr-comment が担う）。

---

## 入力（引数）

- 引数に PR 番号（例 `1682`）または PR の URL があればそれを対象にする。
- 引数が無ければ、現在のブランチに紐づく PR を `gh pr view --json number,url,title,state,isDraft` で特定する。
  特定できなければ、ユーザーに対象 PR を確認して中止する（推測で別 PR をレビューしない）。
- `--reviewer <CLI名>`（複数回指定可）: フェーズ1-B で起用する外部ハーネス。tui-harness のカタログ
  （`catalog.sh`）にある CLI 名で指定する。**同一 CLI の重複指定は中止**。省略時は codex 1体。
- `--model <CLI名>=<モデル>`（複数回指定可）: 当該レビュアーのモデルを明示指定する。キーの CLI 名が
  起用レビュアー（`--reviewer` の指定、無指定なら codex）に含まれなければ中止。値の検証はフェーズ0
  （レビュアー確定チェック）で行う。省略時は当該ハーネスの既定モデル。reasoning effort を持つ CLI は
  モデル値に内包して指定する（例: codex の `<slug>@<effort>` 形）。

## 全体フロー

```
[フェーズ0] TUI 専用ゲート & 前提チェック & 対象PR特定 & レビュアー確定 & PR head worktree & 共有入力パッケージ作成
        │
        ▼
[フェーズ1] 並列実行
   ├─ A: 標準PRレビュー(独立観点 6 体) → findings_review
   └─ B: 外部ハーネス独立レビュー(tui-harness ペイン) → findings_<CLI名>   ※起用不能・失敗の扱いはフェーズ0・1-B の規定
        │
        ▼
[フェーズ2] 機械的マージ & 重複排除（メイン側） → findings_merged
        │
        ▼
[フェーズ3] アーキテクト観点メタ検証（偽陽性除去・抜け漏れ補完・確信度/重要度付与） → findings_verified
        │
        ▼
[フェーズ4] 再ランク（BLOCKER/HIGH/MEDIUM/LOW・全出し・LOW 丸め）
        │
        ▼
[フェーズ5] ドラフト → /plainify で明快化 → 出力（投稿は別スキル pr-comment）
        │
        ▼
[後始末] ペインクローズ → worktree / 一時 ref の削除 → 残ペイン検証（正常終了・途中中止を問わず必須）
```

最初に TODO リスト（フェーズ0〜5 と後始末）を作成してから着手すること。

## フェーズ0: TUI 専用ゲート & 前提チェック & 対象PR特定 & レビュアー確定 & 共有入力パッケージ作成

0. **TUI 専用ゲートと前提スキル tui-harness の解決**。`tui-harness/SKILL.md` を手順 1 と同じ探索順で
   解決して Read し、同梱 `mux.sh` の `detect` を実行する。tui-harness が見つからない、または
   検証済みバックエンドが返らない場合は**レビューを開始せずに中止**し、検証済み TUI マルチプレクサ内
   での再実行または tui-harness の導入（plainify と同じ agent-skills リポジトリ（`tmstack-io/agent-skills`）で配布。
   例: `npx skills add tmstack-io/agent-skills --skill tui-harness`）を案内する。どのマルチプレクサが
   検証済みかの正本は tui-harness であり、本スキルは固有名を前提にしない。TUI 外の代替経路は無い。
   フェーズ1-B は本スキルを tui-harness の**利用スキル**として実行するもので、共通手順
   （ペイン配置・起動・委譲・受理判定・pull 安全網・指揮者裁定・未知ダイアログ・クローズ）の正本は
   tui-harness、ハーネス固有差分の正本は `transports/<CLI名>-tui.md` である。

1. **前提スキル plainify と同梱 verbatim-inputs.md の存在チェック**。本スキルはフェーズ5の明快化で
   agent-skills リポジトリの plainify に依存する。次の順で `plainify/SKILL.md` を探す —
   (1) 本スキルの隣（`../plainify/SKILL.md`。両リポジトリのスキルを同じディレクトリへ
   symlink / コピーしていればここで見つかる）、(2) Claude Code のスキルディレクトリの
   プロジェクト側 → グローバル側（`.claude/skills/plainify/` → `~/.claude/skills/plainify/`）。
   どこにも無ければ**レビューを開始せずに中止**し、復旧手順を案内する
   （agent-skills リポジトリ `tmstack-io/agent-skills` から plainify を導入して再実行。
   例: `npx skills add tmstack-io/agent-skills --skill plainify`）。
   あわせて、本スキル同梱の `verbatim-inputs.md`（フェーズ1・3 で逐語で渡すペイロードの正本。
   自スキルディレクトリ直下）の存在を確認する。無ければ**レビューを開始せずに中止**し、
   本スキルの配布リポジトリ `tmstack-io/claude-skills` からの再取得を案内する
   （逐語ペイロード無しの縮退レビューはしない）。

2. **gh の確認と対象 PR の特定**（上記「入力」参照）。
   最初に `gh` の存在と認証を確認する（`command -v gh` と `gh auth status`）。不可なら処理を
   開始せず、導入・ログイン（`brew install gh` / `gh auth login`）を案内して中止する。
   `gh pr view <PR> --json number,url,title,state,isDraft,baseRefName,headRefName,headRefOid` で取得。

3. **eligibility チェック**（メイン側で判定。取得済み JSON を見るだけなのでサブエージェントは使わない）。
   次のいずれかなら **中止**し、理由を伝える。
   - PR がクローズ済み / マージ済み。
   - PR がドラフトで、かつユーザーがドラフトのレビューを明示要求していない。
   - PR author が bot アカウント（dependabot / renovate 等の自動生成 PR）で、かつユーザーがレビューを明示要求していない。
   deep-pr-review は深いレビューが目的のため、「既に自分でレビュー済み」では中止しない（再レビューを許容）。

4. **レビュアー確定チェック**
   - 起用レビュアーの一覧を確定する: `--reviewer` の指定（同一 CLI の重複があれば中止）、
     無指定なら codex 1体。
   - tui-harness の `catalog.sh probe` を実行する。
     - **明示指定**（`--reviewer` あり）のハーネスが ok でなければ、レビューを開始せず**中止**する。
       excluded の理由と復旧手順（導入・再ログイン等）を提示し、勝手に別の CLI へ差し替えない。
     - **無指定の既定 codex** が ok でなければ、フェーズ1-B を skip する。skip した事実は最終出力の
       `外部レビュー:` 行に必ず明記する（外部レビュー済みと詐称しない）。
   - `--model` の値を検証する（二値）: 指定値を `catalog.sh models <CLI名>` の一覧と照合する。
     reasoning effort に対応する CLI では `<slug>@<effort>` の完全形のみ受け付け、slug 部を一覧と
     照合する（対応可否と形式の正本は `catalog.sh models` の出力と当該 transports。独自の省略形解釈は
     しない）。**完全一致** → 採用。
     **大文字小文字・区切り記号・部分一致のゆれで候補がちょうど1件** → 自動是正して採用し、
     是正内容を報告に明記する。**候補が0件または2件以上** → レビューを開始せず、候補一覧を添えて
     再指定を求める。

5. **PR head worktree の作成**
   観点 #1・#3・#4・#5・#6、外部ハーネス、フェーズ3 の architect は **PR 適用後のファイル・履歴** を参照する。
   現在の作業ツリーが対象 PR と別ブランチだと読む内容がズレるため、PR head を専用の
   git worktree に展開する。作業ツリーは汚さない（現在ブランチを切り替えない）。
   ```sh
   # BSD/GNU 両実装で通る template 形式（-t 形式は GNU mktemp で失敗する）
   WT_DIR="$(mktemp -d "${TMPDIR:-/tmp}/deep-pr-review-wt.XXXXXX")"
   # pull/<番号>/head は同一リポPR・フォークPRの双方で解決できる。
   # 先頭の + は必須（再実行時に PR head が進んでいても強制更新する。無いと non-fast-forward で失敗する）
   git fetch origin "+pull/<PR番号>/head:refs/deep-pr-review/<PR番号>"
   git worktree add --detach "$WT_DIR" "refs/deep-pr-review/<PR番号>"
   ```
   - **remote 名は PR の取得元に合わせる**: 通常は `origin` でよいが、origin が PR のあるリポジトリを指していない fork 運用（upstream 等）では、`git remote -v` と PR の URL を突合して該当 remote 名に読み替える。
   - **サブエージェントの cwd は指定できない**（セッションの cwd を引き継ぐ）。「$WT_DIR で動かす」は
     プロンプト側で担保する: ファイルを読む各エージェントのプロンプトに `$WT_DIR` の絶対パスを明示し、
     「ファイル参照は `$WT_DIR` 配下の絶対パス、git 操作は `git -C "$WT_DIR"` で行い、
     それ以外の作業ツリーは読まない」ことを指示する。
   - フェーズ1-B のハーネスは cwd を `$WT_DIR` に固定して起動する（詳細はフェーズ1-B）。
   - **フォールバック**: worktree 作成に失敗した場合のみ、作業ツリーがクリーンなことを確認の上
     `gh pr checkout <PR番号>` で切り替え、**終了時に必ず元ブランチへ戻す**。この経路では
     **フェーズ1-B を skip する**（外部ハーネスの書き込み安全は「cwd が使い捨て worktree である」
     ことを前提としており、実作業ツリーを cwd にする委譲はしない）。skip は `外部レビュー:` 行に
     明記する。checkout 経路では、各観点・architect へ渡す `$WT_DIR` をリポジトリルートの
     絶対パスに読み替える。それも不可なら「差分のみで継続（ファイル本体は未参照）」とし、
     `$WT_DIR` を要する観点 #1・#3・#4・#5・#6 は skip して #2 のみ実行し、skip した観点と
     制約を最終出力の `注記:` に明記する。
   - **後始末は末尾の「後始末」節を参照。正常終了か途中中止かを問わず必須。**

6. **共有入力パッケージの作成**（メイン側。以降のレビューエージェント・外部ハーネス・architect にはこれを渡す）
   1. **差分ファイル** — 取得は 1 回だけ。以降の全員がこのファイルを参照する:
      ```sh
      DIFF_FILE="$(mktemp "${TMPDIR:-/tmp}/deep-pr-review-diff.XXXXXX")"
      gh pr diff <PR番号> > "$DIFF_FILE"
      ```
   2. **PR 要約** — `gh pr view` の title/body と `$DIFF_FILE` から数行で作成する。
   3. **ルールパス一覧** — `$WT_DIR`（PR head 側）のリポジトリルートの CLAUDE.md / AGENTS.md、
      PR が変更したディレクトリ配下の CLAUDE.md / AGENTS.md、`.claude/rules/` 配下
      （存在すれば。特定プロジェクト名は前提にしない）のパス一覧。
      中身ではなくパス一覧を渡し、各エージェントが必要に応じて自分で読む。
   4. **diff サイズガード** — `wc -l < "$DIFF_FILE"` で規模を確認する。極端に大きい場合
      （目安: 3,000 行超 もしくは 40 ファイル超）は、変更ファイル群を観点ごとに分割するか、
      生成物・lockfile・自動生成コード等を対象外に絞る。
      絞った場合は対象外にしたものを最終出力の `注記:` に明記する（黙って切り捨てない）。
   5. **PR 本文の逐語** — `gh pr view <PR番号> --json body --jq .body` で取得する
      （観点 #6 とフェーズ3の architect に渡す）。

## フェーズ1: 並列実行（A と B を同時に走らせる）

A の 6 体（独立コンテキストのサブエージェント）と B のハーネス委譲（シェル実行）は独立している。
まず A の 6 体を背景で起動し、その裏で B の委譲ハンドシェイク（ペイン起動→ブリーフ送信→受理確認→
安全網）を進める。

### A: 標準 PR レビュー（独立観点 6 体・固定）

通常の `/review`（組み込み）は結果を PR コメントとして投稿し、構造化された findings が手元に残らない。
そのため **`/review` を呼ばず、その多観点レビューを内包実行**して findings を構造化データとして保持する。

**共通仕様**（全レビューエージェントに適用）:

- 独立コンテキストの読み取り専用サブエージェントとして起動する（Claude Code では Agent ツール・
  `subagent_type: general-purpose`。起動できない環境は「フォールバック規定」へ）。
  model は指定しない（セッションの model を引き継ぐ）。
- プロンプトに **読み取り専用**（編集・書き込み・コミット禁止）を明記する。
- 入力: PR 番号 / `$DIFF_FILE` / `$WT_DIR` / PR 要約 / ルールパス一覧 /
  `verbatim-inputs.md` の「偽陽性として扱う例」（逐語）。
- 返却フォーマット（逐語で指定する。フェーズ2の機械的マージが崩れないよう厳守させる）:
  ```
  - 観点: #<番号>
    file: <パス>:<行 or 行範囲>
    要約: <一行>
    理由: <なぜ問題か。事実ベースで具体的に>
    推奨修正: <どう直すか>
  ```
  指摘が無ければ「指摘なし」とだけ返させる。

**観点の割り当て**（6 観点）:

- #1: CLAUDE.md / `.claude/rules/` への準拠監査（CLAUDE.md は実装ガイドのため、レビューに無関係な項目は除外する）。
- #2: 変更差分のみを読んだ素朴なバグスキャン（大きなバグ重視。些末な指摘・偽陽性は避ける）。
  この観点のみ `$DIFF_FILE` だけで完結し、`$WT_DIR` を読む必要はない。
- #3: 変更箇所の履歴に照らしたバグ検出。**変更行の由来は base 側で見る**:
  `git -C "$WT_DIR" blame <baseRefName> -- <パス>` や `git -C "$WT_DIR" log -L`。
  （PR head で blame すると変更行は PR 自身のコミットに帰属し、歴史的文脈が読めない。）
- #4: 同じファイルを触った過去 PR のコメントを読み、本 PR にも当てはまる指摘を検出。取得手順:
  `git -C "$WT_DIR" log <baseRefName> --format=%H -- <パス>` で当該ファイルの過去コミットを列挙 →
  `gh api "repos/<owner>/<repo>/commits/<sha>/pulls"` でコミットから PR を逆引き →
  `gh api "repos/<owner>/<repo>/pulls/<PR番号>/comments"` で当該 PR のレビューコメントを読む。
  当てはまりの確認には `$WT_DIR` のコードを参照する。
- #5: 変更ファイルのコードコメントを読み（`$WT_DIR` 配下）、コメントのガイダンスに反していないか確認。
- #6: 差分外整合（差分の外側との突き合わせ。`$WT_DIR` を必ず読む。入力には共通仕様に加えて
  共有入力パッケージの **PR 本文の逐語** を渡す）。次の 2 つを行う:
  1. **兄弟実装スイープ** — 差分中の防御的変更（ガード・正規化・エスケープ・型チェック・
     直列化済み入力の復元対策等の追加）を列挙し、それぞれについて同じデータソース
     （key-value ストアのキー・GET/POST パラメータ・テーブル・定数・ワイヤ形式）を読み書きする差分外の箇所を
     `$WT_DIR` から検索し、同じ防御が無い非対称を指摘する。PR が片側にだけ防御を足した事実は、
     兄弟側に同じ欠陥が残っている手がかりとして扱う。
  2. **PR 本文整合** — PR 本文の検証可能な逐語の主張（「〜は使っていない」「〜と同仕様」
     「〜を確認済み」等）を列挙し、最終差分と `$WT_DIR` のコード実体に照らして食い違いを指摘する。
     理由に重要度の目安を添える: 記録の正確性に留まる食い違いは LOW 相当、動作保証・セキュリティ・
     性能に関わる主張の食い違いは MEDIUM 相当（最終的な重要度はフェーズ3が付与する）。

**この段階では採点もフィルタもしない。** 確信度・重要度のフィールドとしての付与はフェーズ3で
architect が一元的に行う（観点 #6-2 が理由内に添える重要度の目安は参考情報であり、フェーズ3を
拘束しない）。
6 体の返却をまとめて `findings_review` とする（各指摘: 出所=review#観点 / file:line / 要約 / 理由 / 推奨修正）。

### B: 外部ハーネス独立レビュー（tui-harness）

フェーズ0で確定したレビュアーごとに、tui-harness のペインで独立レビューを委譲する
（フェーズ0で skip が確定したレビュアーは除く）。共通手順の正本は tui-harness（フェーズ0で Read 済み）。

**呼び出しパラメータ（tui-harness の3値）**:

- **成果物置き場**: `$WT_DIR/.deep-pr-review/`（実行中の仮置き。後始末の worktree 削除で消える）。
- **push ラベル**: `dpr-<CLI名>`。
- **裁定スコープ**: tui-harness の既定（成果物置き場への書き込み＋通信規約の push コマンドのみ許可）。

**cwd**: transports の起動コマンドにある `<プロジェクトルート>` は **`$WT_DIR` に展開**する
（PR head worktree を、この委譲における作業対象プロジェクトのルートとして扱う）。

**手順**:

1. 成果物置き場 `$WT_DIR/.deep-pr-review/` を作成し、レビュアーごとのブリーフを
   `$WT_DIR/.deep-pr-review/brief-<CLI名>.md` に書く。含めるもの:
   - PR 要約・ベースブランチ・`$DIFF_FILE` の絶対パス。cwd（`$WT_DIR`）が PR 適用後のリポジトリである旨。
   - レビュー依頼本文: 「`$DIFF_FILE` の差分を一から独立にコードレビューせよ。バグ・設計上の問題・
     セキュリティ・整合性・より単純な代替案の観点で指摘し、各指摘に対象ファイルと行(file:line)・
     問題の理由・推奨修正を付けよ。出力は正しく分かりやすい日本語で、コード識別子や固有名詞は
     原語のまま記載せよ。」
   - 返却フォーマット: フェーズ1-A と同一の構造（逐語で指定。`観点:` は `外部` とする）。
     回答は自由文のレビューではなくこの構造のみで返させ、指摘が無ければ「指摘なし」とだけ書かせる。
   - `verbatim-inputs.md` の「偽陽性として扱う例」（逐語・全文）。
   - 回答ファイルパスの指定: `$WT_DIR/.deep-pr-review/findings-<CLI名>.md`。
   - 書き込み規律: 「書いてよいのは `$WT_DIR/.deep-pr-review/` 配下のみ。コードの編集・コミットは禁止。
     確認は読み取り専用の調査に限る。」
   - 自律完走指示: 「原則質問せず、不明点は前提を明記した上で完走せよ。」
   - 通信規約ブロック（tui-harness の規定を一字一句コピーし、`<>` を実値に置換）。
2. tui-harness の規定どおりペインを配置・起動し（`--model` 指定があれば当該 transports の規定で
   起動コマンドへ反映する）、ブリーフの実行を委譲して受理を確認し、pull 安全網を張る。
   安全網のタイムアウト・発火時の三分類・延長1回の上限は tui-harness の規定に従う。
3. **回収**: `[dpr-<CLI名>] done` の push（または安全網発火時の直接回収）で回答ファイルを Read し、
   `findings_<CLI名>`（各指摘: 出所=<CLI名> / file:line / 要約 / 理由 / 推奨修正）として保持する。
   question の push が届いたら回答を返して続行する。
4. **失敗規律**: 受理の再送上限・安全網の延長上限（いずれも tui-harness の規定）を消化しても
   完了しないレビュアーは skip 扱いとし、ペインの画面内容に基づく理由を `外部レビュー:` 行に明記する。
   他のレビュアーとフェーズ1-A は続行する。
5. **汚染検査**: 全レビュアーの回収（または skip 確定）後、`git -C "$WT_DIR" status --porcelain` を
   実行し、`.deep-pr-review/` 以外に差分があれば「ハーネスによる規律外の書き込み」として最終出力の
   `注記:` に警告を明記する（worktree は使い捨てのため実害は波及しないが、黙って流さない）。
6. **クローズ**: 回収（または skip 確定）の完了後、フェーズ2の開始前に、本スキルで開いた全ペインを
   tui-harness の規定でクローズする。以降のフェーズでハーネスへ追質問はしない。

## フェーズ2: 機械的マージ & 重複排除（メイン側）

`findings_review` と各レビュアーの `findings_<CLI名>` をマージし、**同一 file:line かつ同趣旨**の指摘を 1 件に統合する。

- 統合時は出所を併記し（例「review#2 / codex」）、最も具体的な説明・推奨修正を採用する。
- 複数出所が同じ問題を挙げた事実は指摘に残す（フェーズ3で確度の補強材料になる）。
- 内容の真偽判断はここではしない（フェーズ3の仕事）。機械的な同一性統合のみ行う。

結果を `findings_merged` とする。

## フェーズ3: アーキテクト観点メタ検証

独立コンテキストのサブエージェントを 1 体起動し（Claude Code では Agent ツール・
`subagent_type: general-purpose`・`model: opus`。起動できない環境は「フォールバック規定」へ）、
`findings_merged` をメタ検証させる。

サブエージェントには次のシステムプロンプトでアーキテクト観点を与える。

> あなたは経験豊富なソフトウェアアーキテクト兼コードレビュー監査役である。**読み取り専用**で作業し、いかなるファイルも変更しない（編集・書き込み禁止）。設計の欠陥・抜け漏れ・整合性・依存リスク・より単純な代替案の観点を重視する。

**渡すもの**: `$WT_DIR`（PR 適用後のコードはこの配下を絶対パスで読む）/ `$DIFF_FILE` / PR 要約 /
PR 本文の逐語（共有入力パッケージのもの）/ ルールパス一覧 / `findings_merged` /
`verbatim-inputs.md` の「確信度ルーブリック」（逐語）/ 同「偽陽性として扱う例」（逐語）。

**求めること**:

- **偽陽性の除去**: 各指摘が実在の問題かを差分と `$WT_DIR` の該当コードに照らして検証し、
  確信度 0–24 相当（「偽陽性として扱う例」に該当するもの。既存からの問題・PR 未変更行への
  指摘も同リストに従うが、同リストの未変更行例外に該当する場合は落とさない）を落とす。
- **抜け漏れの補完**: 既存指摘が見落とした設計上の欠陥・整合性・依存リスク・より単純な代替案を
  新規指摘として追加する（出所=architect）。新規指摘には根拠となる file:line を必須とする。
  出所=architect の指摘は第三者の検証を経ない単独観点である（意図した非対称。読み手は
  出所ラベルで判別できる）。
- **推奨整合の検証**: 残す各指摘について、`推奨修正:` を `理由:` の機序に代入し、機序が主張する
  故障シナリオがその修正後も成立しなくなることを 1 手ずつ確認する。修正後もシナリオが成立する
  （例: 実行順・タイミングの前提と推奨が矛盾する）場合は推奨を差し替え、確実な差し替え先が
  無ければ `推奨修正: なし（要設計判断: <理由>）` とする。機序と矛盾した推奨をそのまま
  通してはならない — 誤った推奨は後続の修正と修正検証の両方を誤らせる。
- **実データ観測の扱い**: DB 等の実データの観測は、問題の**存在**の確信を上げる根拠にはできるが、
  **不存在**の根拠にはできない。現行データに該当状態が無いことは「発生条件が未充足」であって
  「構造上発生しない」ではない。これを理由に確信度を下げる場合は、発生条件の到達可能性
  （誰が・どの操作でその状態を作れるか）を評価して理由に明記する。
- **確信度・重要度の付与**: 残った全指摘に、ルーブリックに基づく確信度（0–100）と
  重要度（BLOCKER/HIGH/MEDIUM/LOW）を付ける。

返却フォーマットは、フェーズ1-A の構造に `出所:` `確信度:` `重要度:` を加えたものを逐語で指定する。
結果を `findings_verified` とする。

## フェーズ4: 再ランク（メイン側）

`findings_verified` を次の 4 階層に並べる。**重要度によるフィルタはしない（全出し）**。
ただしフェーズ3で偽陽性と確定したものは出さない。

- **BLOCKER**: 確実なバグ・データ損失・セキュリティ欠陥など、マージ前に必ず直すべき重大問題。
- **HIGH**: 高確信の実バグ。実運用で踏む可能性が高く、現状の実装では不十分。
- **MEDIUM**: 実害はあるが頻度が低い／影響が限定的。
- **LOW**: nitpick・様式・低確信。直すと良いが必須ではない。

各階層内は確信度の高い順に並べる。並び順の確定後、全指摘に**指摘ID**を付与する —
重要度接頭辞（B/H/M/L）＋階層内連番（並び順どおり 1 始まり。例: B1 / H2 / M3 / L12）。
指摘ID は選別（pr-comment）で個別指摘を指す識別子であり、直近の統合レビュー出力内でのみ有効
（再実行時は振り直す）。フェーズ2〜3の内部データには持ち込まない（内部の突合は従来どおり
file:line と出所で行う）。

- **LOW の肥大化対策**: フィルタはしないが、LOW が多数（目安 8 件超）になった場合は、
  LOW のみ「同種をまとめた要約＋代表 file:line」に丸めてよい。BLOCKER/HIGH/MEDIUM は丸めない。
  丸めは指摘ID の付与後に行い、丸めた場合は LOW 見出しに被覆する指摘ID の範囲と件数を
  「(L5〜L12 の 8 件を要約)」の形で明記する（黙って落とさない）。丸め前の個別指摘
  （指摘ID・file:line・要約・理由・推奨修正）はセッション文脈に残り、pr-comment が指摘ID 指定で
  解決する。

## フェーズ5: ドラフト → /plainify で明快化 → 出力

統合レビュー1本を内部ドラフトとして作り、`/plainify` スキルの整形規則を適用してから最終出力する。
**本スキルは PR へコメントを投稿しない**（投稿は別スキル pr-comment の責務）。

### 1. ドラフト作成

フェーズ4の結果を下記「出力フォーマット」へ流し込み、統合レビューのドラフトを作る。この時点では完璧な日本語にこだわらず、各指摘の「**何が・どこで(file:line)・なぜ問題か・どう直すか**」を漏れなく構造化することを優先する。

### 2. /plainify による明快化（日本語の品質担保）

統合レビューのドラフト全体に `/plainify` の整形規則を適用してから最終出力する。
plainify は本スキルと**同一コンテキストで動く事後リライト規則**であり、別プロセスではない
（Skill ツール等での別呼び出しにはしない）。つまり「渡す」とは、フェーズ0の手順 1 で解決した
`plainify/SKILL.md` を **Read し**、その規則を**この統合レビューに対する最終整形パスとして
同一コンテキストで適用する**ことを指す（意味厳守＝指摘の数・強度・条件・例外・数値・評価語を変えない）。

各指摘の指摘ID・`出所`・`確信度: NN`・重要度見出しとセクション構造は読み手の判断材料であり、
plainify の既定（構造化された出所・確信度等のラベルは保持する）どおり保持する
（内部タグとみなして削らない）。

### 3. 出力

整形済みの統合レビュー1本のみをターミナルに出力する。

### 4. 投稿の案内と終了

出力の末尾で「選んだ指摘を PR へ投稿する場合は `/pr-comment`（例: `/pr-comment M1,M3`。
`mediumの3点` のような階層指定も可）」と一行案内し、この後「後始末」を実行して終了する。

## 後始末（必須。正常終了か途中中止かを問わず実行する）

1. **ペインのクローズ**: フェーズ1-B 手順6で未クローズのペインが残っている場合（エラー・中止で
   フローが中断した場合を含む）、`mux.sh list` で ID を取り直し、対応表に載る全ペインを
   `mux.sh close` する。途中中止では未回収の委譲が残っていても**強制クローズ**してよい
   （tui-harness のクローズ3条件は正常フロー用の規定）。その場合は委譲を放棄した旨を報告に含める。
2. **worktree と一時 ref の削除**（成果物置き場 `.deep-pr-review/` も worktree ごと消える）:
   ```sh
   git worktree remove --force "$WT_DIR"
   git update-ref -d refs/deep-pr-review/<PR番号>
   ```
3. **残ペインの最終検証**: `mux.sh list` を取り、対応表のペインが1つも存在しないことを確認してから
   完了（または中断）を報告する。残っていればその場で close する。

worktree 作成前に中止した場合（eligibility 不適合等）は手順2は不要、ペイン起動前の中止なら
手順1・3も不要。worktree フォールバック（`gh pr checkout`）を使った場合は、手順2の代わりに
**元ブランチへ戻したことを確認**する。エラーでフローを中断する場合も、中断を報告する前に
この後始末を実行する。

## フォールバック規定

外部レビューの中止・skip 条件と明記義務はフェーズ0・1-B に従う。ここでは残る1ケースのみ規定する:

- サブエージェントを起動できない環境では、その旨を明記した上で、メイン側が観点別レビュー（フェーズ1-A 相当）とメタ検証（フェーズ3 相当）を**別々のパスに分けて**代替する（レビューと検証を同一パスで済ませる自己承認を避け、代替であることを詐称しない）。
