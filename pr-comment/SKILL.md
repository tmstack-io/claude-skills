# pr-comment

deep-pr-review（レビューの生成と提示）から責務分割した投稿側のスキル。同一セッションの統合レビューを
入力とし、ユーザーが選んだ指摘だけを GitHub PR へレビューコメントとして投稿する。

本スキルは作業ツリー・git 履歴には一切触れない（成果物は PR 上のコメントのみ）。
worktree も作らない（必要なコード文脈は PR 差分で足りる）。

**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨できる選択肢がある場合は理由を一言添えて明示し、ツールを呼ばずターンを終了してテキスト回答を待つ。複数項目の一覧は、1項目を「見出し行（識別子と主情報）＋属性ごとの下位箇条書き」の1ブロックで書き、1行に1属性とする（Markdown は単一改行を結合するため、改行は箇条書き構造または空行で確保する）。以下で「散文提示」はこの形式を指す。

---

## フロー概観

- **選別指定あり**: 前提と中止条件 → 選別指定の解釈 → アンカー行の解決 → 二重投稿の防止 →
  復唱と最終確認 → 公開整形 → 投稿 → 報告と後始末
- **選別指定なし**: 前提と中止条件 → **一次選択**（軽量な候補一覧で先に選ばせ、回答は
  「選別指定の解釈」の記法で読む）→ アンカー行の解決 以降は同じ

以降の節で**投稿候補**とは、選別指定から確定した指摘（選別指定なしの起動では一次選択で選ばれた
指摘）を指す。

---

## 入力（引数）

- **選別指定**（任意）: 投稿対象の指摘を指摘ID または自然言語で指定する。記法は「選別指定の解釈」節。
  省略時は「一次選択」節へ進む。
- **PR番号|URL**（任意）: 指定時は対象レビューの PR と突合し、**不一致なら中止**する
  （誤 PR への公開投稿を防ぐ二重チェック。指定が無ければセッション文脈の PR をそのまま使う）。

引数の読み分け: 数値のみ・URL の引数は PR の指定として読む。選別指定は指摘ID か階層名を含む形で
受け取り、どちらとも取れる場合は推測せず復唱で確認する。

---

## 前提と中止条件（前置きゲート）

順に確認し、満たせなければ**投稿を開始せずに中止**する。

1. **対象レビューの存在**: 同一セッションの会話文脈に deep-pr-review の統合レビュー出力
   （冒頭の `対象:` から始まる見出し行に PR URL と `head:` の値を含み、重要度階層・指摘ID を
   持つもの）があること。無ければ deep-pr-review の実行を案内して中止する
   （**指摘を推測で再構成しない**）。複数ある場合は直近の出力を対象とする。
2. **publish-polish の解決**（必須依存）: 同フォルダの `partial-application-contract.md`
   （publish-polish 部分適用契約の正本）を Read し、その「publish-polish の解決手順」に従って
   `publish-polish/SKILL.md` を解決する。解決できなければ同手順の規定どおり中止する。
3. **gh の確認**: `command -v gh` と `gh auth status`。不可なら導入・ログインを案内して中止する。
4. **PR の特定と突合**: 対象レビュー冒頭の見出し行
   （`対象: <PR URL> / ベースブランチ: … / head: …` の形式）に含まれる PR URL から
   PR 番号と `<owner>/<repo>` を確定する。
   引数に PR番号|URL があれば突合し、不一致なら中止する。**以後の全 `gh` コマンドには
   `--repo <owner>/<repo>`（API 形式は `repos/<owner>/<repo>/...`）を明示し、cwd のリポジトリに
   依存しない**（cwd が別リポジトリのセッションで誤った PR を引かないため）。
5. **鮮度ガード**: `gh pr view <PR番号> --repo <owner>/<repo> --json state,headRefOid` を取得し、
   - `headRefOid` が対象レビューの `head:` の値と**不一致なら中止**し、deep-pr-review の再実行を促す
     （レビューが検証していないコードへの投稿になるため）。`head:` の値が無い出力（旧フォーマット）も
     突合不能として同様に中止する。
   - `state` が closed / merged なら、その事実と「続行する」「中止する」の二択を散文提示で
     確認する（マージ後の申し送り投稿は正当な用途としてありうる）。

完了条件: 上記 5 項をすべて通過し、`<owner>/<repo>`・PR 番号・突合済みの `headRefOid` が
確定している。

---

## 選別指定の解釈

**指摘ID 指定を正準とする**。指摘ID は対象レビューの各指摘に付く「重要度接頭辞＋階層内連番」の
識別子（B1 / H7 / M3 / L12）。どの記法で指定されても、復唱・最終確認では指摘ID の列挙に確定させる。
受け付ける記法（寛容に解釈する）:

- 指摘ID の列挙 — `M1,M3`（大文字小文字は区別しない。`m1` も `M1` と解釈する）
- 指摘ID の範囲 — `L5-L12`（同一階層内の連番範囲）
- `<階層>のN点` — 当該階層の**上位N件**（階層内は確信度の高い順に並んでいる）
- `<階層>の1,3` — 階層内の**連番指定**（指摘ID の数字部と同じ）
- `全部` / `<階層>全部` / 階層と指摘ID の併記・混在（例: `blockerとhighの全部`、`blockerの全部とM3`）

階層名は対象レビューの見出しどおり `BLOCKER / HIGH / MEDIUM / LOW`（大文字小文字・日本語混じりは
寛容に解釈し、復唱で確定する）。`全部` / `<階層>全部` は丸め済み LOW を**含む**全件を指す
（丸めは表示の圧縮にすぎない）。解釈があいまいな場合（階層名の無い「3点」等）は**推測せず**、
復唱時に候補を並べて確認する。対象レビューに存在しない指摘ID（例: MEDIUM が 3 件しかない
レビューへの `M9`、範囲指定の一部欠落）は、近い指摘に読み替えず解決不能として扱い、当該分のみ
見送って復唱で「レビューに該当なし」と明示する。

**丸め済み LOW の解決**: 対象レビューで LOW が「同種をまとめた要約」に丸められている場合も、
丸め見出しに明記された被覆範囲（例「(L5〜L12 の 8 件を要約)」）の指摘ID で個別に指定できる。
解決は同一セッション文脈に残る丸め前の個別指摘（deep-pr-review が指摘ID 付与済み）から行い、
file:line・要約・理由・推奨修正を**一字一句変えずに**用いる（文脈からの逐語復元であり、推測での
再構成ではない）。文脈に丸め前の個別指摘が見つからない指摘ID は解決不能として当該分のみ見送り、
復唱で明示する。

## 一次選択（選別指定なしの起動のみ）

指摘ID・重要度・一行要約だけの候補一覧を、切り捨てず全件、散文提示して投稿したい指摘ID の回答を
待つ（属性がこの3点だけなので、各項目は見出し行1行のブロックでよい。この時点ではアンカー解決・
既存コメント突合をまだ行わない — 下調べの量を実際に投稿する件数に比例させるため）。対象レビューで LOW が丸められて
いる場合も、一覧にはセッション文脈に残る丸め前の個別指摘を指摘ID 単位で展開して並べる（丸めは
表示の圧縮にすぎない）。文脈から復元できない指摘ID は一覧に「解決不能」と明示する。回答の解釈は
「選別指定の解釈」の記法に従う。回答が 0 件なら、アンカー行の解決へ進まずその旨を報告して終了する。

完了条件: 対象レビューの全指摘（丸め前の個別指摘を含む）が一覧に現れたうえで、投稿したい
指摘ID の集合が回答から確定している（投稿はまだ確定しない — 最終確認は「復唱と最終確認」で行う）。

---

## アンカー行の解決

投稿候補それぞれについて、PR 差分内の**アンカー行**を先に解決する（GitHub のレビューコメントは
**PR の差分に含まれる行にしか付けられない**）。解決結果は復唱・最終確認に含める。

差分はレビュー実施時のものを再利用せず、本スキルの実行時にアンカー解決の直前で**一度だけ**取得する。
ユーザーの回答待ち（一次選択等）を挟んで再開した場合は、取得の前に
`gh pr view <PR番号> --repo <owner>/<repo> --json headRefOid` を取り直し、前置きゲート5で突合した
値と一致することを確認する（不一致なら投稿せず中止し、deep-pr-review の再実行を促す。一致して
いれば差分の内容はレビュー時と一致する）:

```sh
# パスは固定の導出規則とする（乱数や変数の持ち越しに依存しない）。Bash 実行はコマンドごとに
# 独立したシェルで変数が失われるため、以後の Read・後始末もこの規則から同じパスを導出する
DIFF_FILE="${TMPDIR:-/tmp}/pr-comment-diff-<PR番号>.diff"
gh pr diff <PR番号> --repo <owner>/<repo> > "$DIFF_FILE"
```

`$DIFF_FILE` は Read で全文を読もうとしない（Read は先頭の一定行数しか返さず、変更ファイルの
多い PR では後半の hunk を取りこぼす）。まず `grep -n '^+++\|^@@' "$DIFF_FILE"` でファイル境界と
hunk ヘッダの一覧を取り、当たりを付けた範囲だけを Read する。hunk ヘッダ
（`@@ -旧開始,旧行数 +新開始,新行数 @@`）からは変更前・変更後**両方**の行範囲を割り出し、
`side=RIGHT`（追加行・文脈行）には**変更後**の行番号を、`side=LEFT`（削除行）には**変更前**の
行番号を渡す。アンカー先は次の順で決める。

1. 指摘の `file:line` が差分の変更行に含まれる → その行
   （追加行・文脈行は `side=RIGHT`、削除行は `side=LEFT`）。
   指摘が**行範囲**（例 `120-130`）の場合は、範囲内の変更行のうち**先頭行**にアンカーする
   （範囲全体を示す必要があるときのみ、投稿時に `-F start_line=<範囲内先頭の変更行>` を併用した
   複数行コメントにしてよい。その場合 `line` には範囲内末尾の変更行を渡す）。
2. 含まれないが、同じ PR が変更した**因果的に最も近い行**がある → その行にアンカーし、
   本文の冒頭で本来の対象（`パス:行`）を明示する。近さは「定義元 → 判定・呼び出し元 →
   同一ファイルの関連行」の順に選ぶ。
3. 差分内に関連行が一切ない（コミットメッセージ・PR 本文・Issue 運用への指摘など）
   → 行アンカーを諦め、`gh pr comment` の会話コメントにフォールバックする。本文の冒頭で対象
   （`パス:行`。差分外の対象なら何についての指摘かを一句で）を明示する — 会話コメントには
   `path` / `line` のメタデータが付かず、本文だけが対象を伝える（pr-recheck もこの明示を
   追跡の起点にする）。

完了条件: 投稿候補の全件に、アンカー先（`パス:行`＋side）または会話コメントへのフォールバックの
いずれかが決まっている（黙って落とした候補が無い）。

---

## 二重投稿の防止

投稿候補について、**「アンカー行の解決」の直後・候補一覧の提示（「復唱と最終確認」）の前に**
既存コメントを取得し、同趣旨の指摘が投稿済みでないか確認する（確認後に候補を黙って減らさない —
除外は最終確認の時点でユーザーに見えていなければならない）。

```sh
# --paginate で全件取得する（既定のページサイズで打ち切らせない。--jq はページごとに適用される）
gh api --paginate "repos/<owner>/<repo>/pulls/<PR番号>/comments" --jq '.[] | "\(.html_url) \(.path):\(.line) \(.body[0:80])"'
gh api --paginate "repos/<owner>/<repo>/issues/<PR番号>/comments" --jq '.[] | "\(.html_url) \(.body[0:80])"'
```

同趣旨のコメントが既にあれば、その指摘を候補から外し、候補一覧に除外として明示する
（表示形式は「復唱と最終確認」のブロック形式に従う）。

完了条件: 既存コメント（レビューコメント・会話コメントとも）を全件取得したうえで、投稿候補の
全件との突合が済んでいる。

---

## 復唱と最終確認

**投稿する指摘をユーザーに選ばせる。選別（解釈の復唱と確認）を経ずに投稿してはならない。**
候補一覧の提示は1回だけ行い、それが解釈の復唱と最終確認を兼ねる（同じ一覧を二度並べない）。

1. 前置きに、投稿先の PR 番号・「選んだ指摘のみを投稿する」こと・自然言語の階層指定の解釈
   （例: 「mediumの3点 → M1, M2, M3 の 3 件」）を書く。
2. 候補全件（切り捨てはしない）を散文提示する。各項目のブロック形式:

   ```
   - **<指摘ID>** [<重要度>] `<パス:行>`
     - 指摘: <いま何が指摘されているか → 投稿すると PR に何が残るか>
     - アンカー先: <`パス:行`＋side、または会話コメントへのフォールバック>
   ```

   二重投稿の防止で除外した指摘は、見出し行を「**<指摘ID>** 投稿済みのため除外 —
   <既存コメントの URL>」として一覧に残す（黙って減らさない）。提示を出力したら、投稿する
   指摘ID のテキスト回答を待つ。
3. 回答が候補一覧に無い指摘ID を含む場合は、その指摘について「アンカー行の解決」「二重投稿の
   防止」を実施したうえで、更新した候補一覧で再度確認を取る。

1 件も選ばれなければ投稿せず、その旨を報告して終了する。

完了条件: 1 件以上が選ばれた場合は、アンカー先・投稿済み除外を含む候補一覧を提示したうえで、
その提示へのユーザーのテキスト回答から投稿する指摘ID の集合が確定している（選別指定なしの
起動では、一次選択の回答だけでは完了としない）。最終確認で 0 件になった場合は投稿せず報告に進む。

## publish-polish による公開整形

選ばれた指摘ごとに投稿本文を作る。deep-pr-review がターミナルへ出した文面をそのまま投げては
いけない。**読者が変わるため**である——ターミナル出力の読者はレビューを依頼した本人だが、
PR コメントの読者は PR の作者と、後から差分を追う第三者である。整形は同フォルダの
`partial-application-contract.md`（publish-polish 部分適用契約の正本。前提ゲート2で Read 済み）の
契約に従う。

本スキルでの三点宣言:

- **想定読者**: PR の作者と、後からこの PR を読むレビュアー。
- **配布形態**: 対象リポジトリの PR に残るレビューコメント。
- **約束するもの**: `file:line` と検証根拠を示し、対応要否を読者が判断できる材料を提供すること。

本スキル固有の適用要点:

- **「内部視点・自己言及」の判定基準（publish-polish のカテゴリ3）を最優先で適用する。**
  レビュー機構の内部語——`出所: review#N / <CLI名> / architect`、`確信度: NN`、`観点 #N`、
  重要度の絵文字見出し、「N 観点が独立に検出」といった記述——は読者の判断に寄与しないため、
  すべて落とす。deep-pr-review のターミナル出力がこれらを保持するのと意図的に異なる
  （ターミナル上ではレビューの確度を示す情報だが、PR 上では内輪の事情でしかない）。
- **保護対象**: `file:line`、識別子、パス、数値、Issue / PR 番号。
- アンカー行と実際の対象行が違う場合は、冒頭で対象を明示する。

完了条件: 選ばれた全指摘の投稿文面が整形済みで、漏えい保留分はユーザーの判断
（修正して投稿 / 見送り）が確定している。

---

## 投稿

**1 指摘 = 1 コメント**で投稿する。複数の指摘を 1 本にまとめない。

1件目を投稿する直前に `gh pr view <PR番号> --repo <owner>/<repo> --json headRefOid` を取り直し、
前置きゲート5で突合した値と一致することを確認する（不一致なら投稿を開始せず中止し、
deep-pr-review の再実行を促す — 最終確認や漏えい保留の回答待ちの間に head が進んでいる場合が
あるため）。

行アンカーの場合:

```sh
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments \
  -f commit_id=<headRefOid> \
  -f path=<差分内のパス> \
  -F line=<行番号> \
  -f side=<side> \
  -f body="$(cat <<'EOF'
<publish-polish 適用後の本文>
EOF
)" --jq '.html_url'
```

- `commit_id` は鮮度ガードで取得した現在の `headRefOid` を使う。
- `path` は**リポジトリルートからの相対パス**。
- `<side>` には「アンカー行の解決」で決めた side（追加行・文脈行は `RIGHT`、削除行は `LEFT`）を渡す。
- 複数行コメント（行範囲アンカー）の場合のみ `-F start_line=<範囲内先頭の変更行>` を加える。
- 本文は heredoc（`<<'EOF'`）で渡す。デリミタをクォートすることで、`$` や backtick を含む
  コード識別子がシェルに展開されるのを防ぐ。
- 422 が返る場合、その行は差分に含まれていない。アンカー解決をやり直すか、会話コメントへ
  フォールバックする。**行番号を当て推量で変えて再試行しない。**フォールバックする場合は、
  投稿前に本文冒頭へ対象（`パス:行`）の明示を追加する（「アンカー行の解決」の分岐3と同じ形式。
  整形済み文面は行アンカー前提で対象明示を持たないため）。
- **422 以外の失敗**（403 の権限不足・認証切れ・レート制限・ネットワーク断など）が出たら、
  残りの指摘の投稿を止める。それまでに投稿できた `html_url` と未投稿の指摘ID を並べて報告し、
  原因と再開方法（原因の解消後、同じ選別指定で本スキルを再実行する — 投稿済み分は
  「二重投稿の防止」で候補から外れる）を添える。

会話コメントへフォールバックする場合も、同じ heredoc 形式で
`gh pr comment <PR番号> --repo <owner>/<repo> --body "$(cat <<'EOF' … EOF
)"` を使う。

完了条件: 選ばれた全指摘について、投稿の `html_url`・会話コメントへのフォールバック（`html_url`
付き）・保留や中断の理由のいずれかが記録されている（結果が無言のまま残る指摘が無い）。

## 報告と後始末

投稿した各コメントの `html_url` を、対応する指摘の要約とともに一覧で報告する。あわせて、
投稿 N 件 / 見送り M 件（解決不能な指摘ID・二重投稿回避・漏えい保留・未選択の内訳）/ 会話コメントへ
フォールバックした件数とその理由を明記する。対象レビューの検出済み全指摘から投稿済みを引いた
集合があれば、階層と指摘ID の列挙で一行想起させる（例: 「未投稿: LOW 7 件 — L1〜L7」。見送り
内訳と重なる分は指摘ID の列挙のみとし重複記載しない。後日、外部レビュアーが同種を指摘した際に、
検出済みだった事実をすぐ引けるようにするため）。この想起行は、投稿 0 件・中止の報告にも含める。
報告の末尾に
「作者の修正が入ったら `/pr-recheck` で修正検証（投稿済み指摘が新 head で解消されているかの
検証と返信）」と一行案内する。

一時ファイルの削除は**正常終了・途中中止を問わず必須**: 本スキルの実行を終える時点（報告または
中止の報告の直前）に `rm -f "${TMPDIR:-/tmp}/pr-comment-diff-<PR番号>.diff"` を実行する
（「アンカー行の解決」の固定の導出規則から同じパスを導出する。シェルを跨いだ変数に依存しない）。
ユーザーの回答を待つためにターンを終了するときは削除しない（再開後のアンカー再解決に使う）。

完了条件: 報告に投稿・見送り・フォールバックの全内訳と各 `html_url` があり、上記の一時ファイルが
削除済み。
