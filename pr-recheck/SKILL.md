# pr-recheck

deep-pr-review（生成）・pr-comment（投稿）から続く追跡側のスキル。投稿済みの指摘コメントが指す
問題が PR の新しい head で解消されているか（修正検証）を二値判定し、ユーザーが選んだスレッドへ
判定つきの返信を投稿する。

**セッションを跨ぐ前提で設計している** — 入力は PR 上のコメントとそのメタデータのみに依り、
同一セッションに deep-pr-review の出力が残っていてもそれを前提にしない（PR 上のコメントだけを
正とする単一挙動）。投稿済みコメントは publish-polish 適用済みで `パス:行`・問題・推奨を自己完結で
含むため、元の指摘ID を復元する必要はない。レビュー時 head は各コメントの `original_commit_id`
から機械的に復元する。

本スキルは作業ツリー・git 履歴には一切触れない（成果物は PR 上の返信と resolve のみ）。
コード参照には使い捨ての worktree を使い、後始末で削除する。新規混入バグの検出は責務外である
（必要なら deep-pr-review の再実行を案内する）。

---

## 入力（引数）

- **PR番号|URL**（任意）: 省略時は現在のブランチに紐づく PR を
  `gh pr view --json number,url` で特定する。特定できなければユーザーに対象 PR を確認して
  中止する（推測で別 PR を対象にしない）。

---

## 前提と中止条件（前置きゲート）

順に確認し、満たせなければ**検証を開始せずに中止**する。

1. **gh の確認**: `command -v gh` と `gh auth status`。不可なら導入・ログインを案内して中止する。
2. **publish-polish の解決**（必須依存）: 次の順で `publish-polish/SKILL.md` を探す —
   (1) 本スキルの隣（`../publish-polish/SKILL.md`）、(2) 実行エージェントのスキルディレクトリの
   プロジェクト側 → グローバル側。どこにも無ければ導入手順
   （`npx skills add tmstack-io/agent-skills --skill publish-polish`）を案内して中止する
   （未整形の内部語混じり文面で返信する縮退はしない）。
3. **PR の特定と状態確認**: `gh pr view <PR番号> --repo <owner>/<repo> --json
   number,url,state,headRefOid,baseRefName` を取得する。**以後の全 `gh` コマンドには
   `--repo <owner>/<repo>`（API 形式は `repos/<owner>/<repo>/...`）を明示し、cwd のリポジトリに
   依存しない**。`state` が closed / merged なら、その事実を提示して**続行可否をユーザーに確認**する
   （マージ後の検証・申し送り返信は正当な用途としてありうる。確認は選択式で行う — Claude Code では
   AskUserQuestion。同等ツールが無い環境では散文で質問し回答を待つ）。
4. **対象コメントの収集**: 認証ユーザー（`gh api user --jq .login`）と author が一致する
   当該 PR のコメントを取得する。いずれも `--paginate` を付け、既定のページサイズで打ち切らせない
   （対象が黙って欠けることを防ぐ）。
   - 行アンカーのレビューコメント:
     `gh api --paginate "repos/<owner>/<repo>/pulls/<PR番号>/comments"` から author 一致分
     （`id` / `path` / `line` / `original_commit_id` / `body` / `in_reply_to_id`）。
     `in_reply_to_id` を持つものは返信であり、指摘の起点（スレッド先頭）のみを検証単位とする。
   - 会話コメント（pr-comment のフォールバック投稿分）:
     `gh api --paginate "repos/<owner>/<repo>/issues/<PR番号>/comments"` から author 一致分。
     会話コメントには `path` / `line` / `original_commit_id` のメタデータが無い。検証対象の位置は
     本文から逐語抽出する（pr-comment は投稿時に対象の `パス:行` を本文冒頭に明示する規定。
     明示が無い指摘は、本文が記述する問題そのものを検証対象とする）。
   0 件なら「検証対象の投稿済み指摘コメントが無い」と報告して中止する
   （deep-pr-review → pr-comment の実行を案内する）。
5. **head の前進確認**: 行アンカーの全対象コメントの `original_commit_id` が現在の `headRefOid`
   と一致する（= 投稿後に head が動いていない）場合、検証すべき修正が存在しない。その旨を報告して
   中止する。会話コメントは `original_commit_id` を持たないためこの確認から除外する
   （対象が会話コメントのみの場合はこの確認を省略して続行する）。

完了条件: 上記 5 項がすべて通過し、対象コメントが 1 件以上ある。

## 検証対象一覧の確定（R 番号）

収集した対象コメントに **R1〜Rn の連番**を振り、一覧を提示してユーザーに確定させる。
以降の復唱・選別・報告は R 番号で行う。

- 各行の形式: `R<n> <パス:行 または 会話コメント> <指摘の一行要旨> / 修正報告: あり(要旨)・なし`。
  `original_commit_id` が現在の `headRefOid` と一致する対象は行末に「head 未前進」と明示する
  （判定は新 head 基準なので実行はできるが、修正が入っていない事実を一覧で判別可能にする）。
- **修正報告の有無**は、行アンカーではスレッド内の返信（`in_reply_to_id` でぶら下がる他者の返信）
  から判定する。会話コメント由来の対象では、当該コメントより後の会話コメントのうち、本文が同一の
  `パス:行`（または当該指摘の内容）に言及するものを返信とみなす。報告は**作者の主張**として一覧に
  添えるのみで、解消の判定には使わない。
- **二重返信の防止**: 自分（認証ユーザー）の検証返信が既に付いている対象（行アンカーはスレッド内、
  会話コメント由来は上記と同じ言及基準で判定）は候補から外し、一覧に「検証返信済み
  （既存返信の URL）」として明示する（黙って減らさない）。
- deep-pr-review 由来でない自分のコメントが混じっている場合、ユーザーはこの一覧で除外を指示できる。

完了条件: 一覧を提示し、ユーザーが対象（除外含む）を確定している。

## worktree の作成（コード参照）

新 head のコードを実体で読むため、使い捨ての worktree を作る。

```sh
# BSD/GNU 両実装で通る template 形式（-t 形式は GNU mktemp で失敗する）
WT_DIR="$(mktemp -d "${TMPDIR:-/tmp}/pr-recheck-wt.XXXXXX")"
# pull/<番号>/head は同一リポPR・フォークPRの双方で解決できる。先頭の + は再実行時の強制更新に必須
git fetch origin "+pull/<PR番号>/head:refs/pr-recheck/<PR番号>"
git worktree add --detach "$WT_DIR" "refs/pr-recheck/<PR番号>"
```

- **remote の突合を常に行う**（worktree 作成の前提）: `git remote -v` の URL と PR の
  `<owner>/<repo>` を突合し、PR のあるリポジトリを指す remote を特定して fetch に使う
  （上記の `origin` は読み替える）。一致する remote が無い場合 — cwd が対象リポジトリの
  クローンでない場合を含む — は、検証を開始せず中止し、対象リポジトリのクローン上での再実行を
  案内する（別リポジトリの同番号 `pull/<N>/head` を fetch する誤検証を防ぐ）。
- 各コメントの検証用**範囲差分**は
  `git -C "$WT_DIR" diff <original_commit_id>..<headRefOid> -- <パス>` で取る。
  `original_commit_id` が履歴に無ければ `git -C "$WT_DIR" fetch origin <original_commit_id>` で
  取得を試みる。それでも取れない場合（force-push で旧 head が到達不能等）、範囲差分なし・
  新 head のコード実体のみで判定する（判定の定義は新 head 基準なのでそのまま成立する）。
  その旨を当該判定の根拠に明記する。
- worktree の作成に失敗したら、検証を開始せず失敗内容を報告して中止する
  （worktree なしの縮退検証はしない）。後始末は末尾の「報告と後始末」節を参照。

## 修正検証（判定）

確定した対象それぞれについて、**読み取り専用サブエージェント 1 体**で検証する
（Claude Code では Agent ツール・`subagent_type: general-purpose`。model は指定しない。
複数体は並列起動してよい。起動できない環境は「フォールバック規定」へ）。

サブエージェントのプロンプトに必ず含めるもの:

- コメント本文（指摘の全文）・`パス:行`（会話コメント由来はゲート4で抽出したもの）・
  `original_commit_id`（行アンカーのみ）・現在の `headRefOid`
- `$WT_DIR` の絶対パスと、「ファイル参照は `$WT_DIR` 配下の絶対パス、git 操作は
  `git -C "$WT_DIR"` で行い、**読み取り専用**（編集・書き込み・コミット禁止）」の指示
- 範囲差分の取得コマンド（上記「worktree の作成」の形）。会話コメント由来は `original_commit_id`
  が無いため範囲差分を渡さず、新 head のコード実体のみで判定させる（その旨を根拠に明記させる）
- 判定の定義（逐語）:

  > 判定は二値である。**解消** = コメントが指摘した問題が、新 head のコードで再現しない
  > （指摘行の周辺実装まで読んで確認する。形だけ変わって問題が残る修正は未解消）。
  > **未解消** = それ以外。部分的な修正も未解消とし、何が残っているかの理由を必須で添える。

- 返却フォーマット（逐語）:

  ```
  R<n>: 解消 | 未解消
  根拠: <新 head のどのコード(パス:行)がどう変わった/変わっていないか。事実ベースで具体的に>
  残る問題: <未解消の場合のみ。何が残っているか>
  ```

完了条件: 全対象に二値判定と根拠が付いている。

## 判定レポートと選別

検証結果を一覧で提示する:
`R<n> [解消|未解消] <パス:行> <一行要旨> / 修正報告: あり・なし / <根拠の要約>`。

返信の**既定候補**は判定×修正報告の有無で組む:

- **解消**（報告の有無を問わず）→ 確認返信＋resolve の候補
- **報告あり・未解消** → 理由返信の候補
- **報告なし・未解消** → 候補にしない（まだ直っていないという催促の公開発信になるため、
  レポートで伝えるのみ。ユーザーが明示的に指示すれば候補に追加できる）

選別はユーザーが R 番号で確定する。**復唱と確認を経ない投稿は禁止**。Claude Code では `AskUserQuestion` を
`multiSelect: true` で使い、選択肢ラベルに R 番号を含める。候補が選択式の上限
（Claude Code では 1 問あたり選択肢は最大 4 件、質問は最大 4 問）を超える場合は選択式を使わず、
候補全件を R 番号付き一覧で散文提示して返信する R 番号の回答を待つ（切り捨てはしない）。
質問文（散文提示の場合はその前置き）に、投稿先の PR 番号・「選んだスレッドのみに返信する」こと・
「解消判定のスレッドは返信後に resolve する（GitHub UI で戻せる）」ことを含める。

1 件も選ばれなければ投稿せず、判定レポートのみで終了する（後始末は実行する）。

## publish-polish による返信整形

選ばれた各返信の文面に、前置きゲートで解決した `publish-polish/SKILL.md` を Read し、
**判定基準（削除候補のカテゴリ判定）と磨き込み基準のみ**を適用する（publish-polish の「フロー」は
既存ファイルの書き換え用なので実行しない。「公開の姿の確認」の質問も行わず、本スキルが次を
前提として宣言する）。

- **想定読者**: PR の作者と、後からこのスレッドを読む第三者。
- **配布形態**: 対象リポジトリの PR レビュースレッドに残る返信。
- **約束するもの**: 検証の判定（解消 / 未解消）と、その根拠となる新 head の `パス:行` を示し、
  スレッドを閉じてよいか読者が判断できる材料を提供すること。

適用時の要点:

- **内部語を落とす**: R 番号・判定機構への言及（サブエージェント・worktree・検証手順等）は
  読者の判断に寄与しないため、すべて落とす。
- **保護対象は一字一句保持する**: `パス:行`、識別子、数値、コミット SHA。
- **判定の実体を変えない**: 解消 / 未解消の判定・根拠・残る問題を増減させない。
- **漏えいの疑いは投稿を保留する**: publish-polish の「要対応」区分に相当する内容を検出したら、
  書き換えず当該返信を保留し、警告を提示してユーザーの判断（修正して投稿 / 見送り）を仰ぐ。
- **各返信を単体で成立させる**: 他の返信への参照を書かない。会話コメントへの返信は、冒頭で
  対象の指摘（`パス:行`）を明示する。

完了条件: 選ばれた全 R の返信文面が整形済みで、漏えい保留分はユーザーの判断
（修正して投稿 / 見送り）が確定している。

## 返信の投稿と resolve

**1 スレッド = 1 返信**で投稿する。複数の判定を 1 本にまとめない。

行アンカーのレビューコメントへの返信:

```sh
gh api "repos/<owner>/<repo>/pulls/<PR番号>/comments/<コメントID>/replies" \
  -f body="$(cat <<'EOF'
<publish-polish 適用後の本文>
EOF
)" --jq '.html_url'
```

会話コメント由来の指摘への返信は、同じ heredoc 形式で
`gh pr comment <PR番号> --repo <owner>/<repo> --body "$(cat <<'EOF' … EOF
)"` を使う（デリミタのクォートで `$` や backtick のシェル展開を防ぐ）。

**解消返信を投稿したスレッドは resolve する**（未解消は返信のみで resolve しない）。
resolve は可逆であり（GitHub UI で unresolve 可能）、スレッド ID は GraphQL で引く:

```sh
# コメントID(databaseId) → スレッドID の対応を取得（100 件超はページングで辿る）
gh api graphql -f query='query($owner:String!,$repo:String!,$pr:Int!){
  repository(owner:$owner,name:$repo){pullRequest(number:$pr){
    reviewThreads(first:100){pageInfo{hasNextPage endCursor}
      nodes{id isResolved comments(first:1){nodes{databaseId}}}}}}}' \
  -f owner=<owner> -f repo=<repo> -F pr=<PR番号>

gh api graphql -f query='mutation($id:ID!){
  resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -f id=<スレッドID>
```

会話コメントにはスレッド resolve が存在しないため、返信のみで完結する。

完了条件: 選ばれた全 R に返信の `html_url` があり、解消分は resolve の返り値で
`isResolved: true` を確認済み（会話コメント由来は返信のみで完結）。

## 報告と後始末

投稿した各返信の `html_url` を、R 番号・判定・対象の要約とともに一覧で報告する。あわせて、
返信 N 件（うち resolve M 件）/ 見送り K 件（検証返信済み・候補外の報告なし未解消・漏えい保留・
未選択の内訳）を明記する。

**後始末（正常終了・途中中止を問わず必須）**:

```sh
git worktree remove --force "$WT_DIR"
git update-ref -d refs/pr-recheck/<PR番号>
```

worktree 作成前に中止した場合は不要。エラーでフローを中断する場合も、中断を報告する前に実行する。

完了条件: 報告に全返信の `html_url` と内訳があり、`git worktree list` に `$WT_DIR` が残っておらず、
`refs/pr-recheck/<PR番号>` が削除済み。

## フォールバック規定

サブエージェントを起動できない環境では、その旨を明記した上で、メイン側が対象を 1 件ずつ順次
検証する（判定の定義と返却フォーマットは同一。代替であることを報告に明記する）。
