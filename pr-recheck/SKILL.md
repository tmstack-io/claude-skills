# pr-recheck

deep-pr-review（生成）・pr-comment（投稿）から続く追跡側のスキル。投稿済みの指摘コメントが指す
問題が PR の新しい head で解消されているか（修正検証）を二値判定し、ユーザーが選んだスレッドへ
判定つきの返信を投稿する。

**セッションを跨ぐ前提で設計している** — 入力は PR 上のコメントとそのメタデータのみに依り、
同一セッションに deep-pr-review の出力が残っていてもそれを前提にしない（PR 上のコメントだけを
正とする単一挙動）。投稿済みコメントは publish-polish 適用済みで `パス:行`・問題・推奨を自己完結で
含むため、元の指摘ID を復元する必要はない。レビュー時 head は各コメントの `original_commit_id`
から機械的に復元する。

本スキルは作業ツリー・git 履歴には一切触れない（成果物は PR 上の返信と resolve のみ）。
コード参照には使い捨ての worktree を使い、後始末で削除する。新規混入バグの検出は責務外である
（必要なら deep-pr-review の再実行を案内する）。

**散文提示**: 本スキルでユーザーに選択・確認を求めるときは、選択肢（または一覧）を空行で区切って
番号を付け、各項目は「現状どうなっているか → 採用・回答すると何がどう変わるか」が再読なしに
分かる完結した文で書き（本スキル内部の言葉にはその場で一言の説明を添える）、推奨できる選択肢が
ある場合は理由を一言添えて明示し、ツールを呼ばずターンを終了してテキスト回答を待つ。
以下で「散文提示」はこの形式を指す。

---

## 入力（引数）

- **PR番号|URL**（任意）: 対象 PR の指定。URL が渡された場合は `<owner>/<repo>` も URL から取る。
  PR 番号のみ・省略の場合、リポジトリは cwd から決め、省略時の PR は現在のブランチに紐づくものを
  使う。特定できなければユーザーに対象 PR を確認して中止する（推測で別 PR を対象にしない）。
  確定の実行はコマンドごと前提ゲート3で行う（本節は引数の意味と決め方の規則のみ）。

以降の全 `gh` コマンドには `--repo <owner>/<repo>`（API 形式は `repos/<owner>/<repo>/...`）を
明示し、cwd のリポジトリに依存しない。

---

## 前提と中止条件（前置きゲート）

順に確認し、満たせなければ**検証を開始せずに中止**する。

1. **gh の確認**: `command -v gh` と `gh auth status`。不可なら導入・ログインを案内して中止する。
2. **部分適用契約と publish-polish の解決**（必須依存）: 次の順で
   `pr-comment/partial-application-contract.md`（publish-polish 部分適用契約の正本）を探して
   Read する — (1) 本スキルの隣（`../pr-comment/partial-application-contract.md`）、
   (2) 実行エージェントのスキルディレクトリのプロジェクト側 → グローバル側。どこにも無ければ、
   導入手順（`npx skills add tmstack-io/claude-skills --skill pr-comment`）を案内して中止する。
   続けて、同ファイルの「publish-polish の解決手順」に従って
   `publish-polish/SKILL.md` を解決する（解決できなければ同手順の規定どおり中止する）。
3. **PR の特定と状態確認**: 「入力（引数）」の規則で PR 番号と `<owner>/<repo>` を確定する
   （省略時の PR は `gh pr view --json number,url`、PR 番号のみ・省略時のリポジトリは
   `gh repo view --json nameWithOwner` で取得）。続けて `gh pr view <PR番号>
   --repo <owner>/<repo> --json number,url,state,headRefOid,baseRefName` を取得する。
   `state` が closed / merged なら、その事実と「続行する」「中止する」の二択を散文提示で確認する
   （マージ後の検証・申し送り返信は正当な用途としてありうる）。あわせて **remote の突合**を行う:
   `git remote -v` の URL と `<owner>/<repo>` を突合し、PR のあるリポジトリを指す remote
   （以降 `<remote>`）を特定する。一致する remote が無い場合 — cwd が対象リポジトリのクローンで
   ない場合を含む — は中止し、対象リポジトリのクローン上での再実行を案内する
   （別リポジトリの同番号 `pull/<N>/head` を fetch する誤検証を防ぐ）。
4. **対象コメントの収集**: 当該 PR のレビューコメントと会話コメントを `--paginate` で**全件**
   取得し（既定のページサイズで打ち切らせない — 対象が黙って欠けることを防ぐ）、`user.login` が
   認証ユーザー（`gh api user --jq .login`）と一致するものを**検証対象**として抽出する。他者の
   コメントは捨てず、修正報告の有無と返信関係の判定材料として保持する。
   - 行アンカーのレビューコメント:
     `gh api --paginate "repos/<owner>/<repo>/pulls/<PR番号>/comments"`
     （`id` / `path` / `line` / `original_commit_id` / `body` / `in_reply_to_id` / `user.login`）。
     `user.login` 一致分のうち `in_reply_to_id` を持つものは返信であり、指摘の起点
     （スレッド先頭）のみを検証単位とする。
   - 会話コメント（pr-comment のフォールバック投稿分）:
     `gh api --paginate "repos/<owner>/<repo>/issues/<PR番号>/comments"` の `user.login` 一致分。
     会話コメントには `path` / `line` / `original_commit_id` のメタデータが無い。検証対象の位置は
     本文から逐語抽出する（pr-comment は投稿時に対象の `パス:行` を本文冒頭に明示する規定。
     明示が無い指摘は、本文が記述する問題そのものを検証対象とする）。本スキルが過去の実行で
     投稿した検証返信（既存の指摘の `パス:行` に言及して解消 / 未解消の判定を述べる自分の
     会話コメント）は検証対象から外し、一覧にも出さない（繰り返し実行で自分の返信に返信を
     重ねない）。
   検証対象が 0 件なら「検証対象の投稿済み指摘コメントが無い」と報告して中止する
   （deep-pr-review → pr-comment の実行を案内する）。
5. **head の前進確認**: 行アンカーの全対象コメントの `original_commit_id` が現在の `headRefOid`
   と一致し（= 投稿後に head が動いていない）、かつ会話コメント由来の対象も無い場合、検証すべき
   修正が存在しない。その旨を報告して中止する。会話コメント由来の対象があれば、行アンカー側が
   全件 head 未前進である事実を報告に添えて続行する（会話コメントはこの確認の対象外）。

完了条件: 上記 5 項がすべて通過し、対象コメントが 1 件以上あり、`<owner>/<repo>`・PR 番号・
`<remote>` が確定している。

## 検証対象一覧の確定（R 番号）

収集した対象コメントに **R1〜Rn の連番**を振り、一覧を散文提示して、除外する R 番号と、
検証返信済みだが再検証したい R 番号（いずれも無ければ「なし」）のテキスト回答を待って確定させる。
再検証に指定された対象は候補に戻し、新 head 基準で通常どおり検証する（前回の検証返信の判定には
縛られない）。以降の復唱・選別・報告は R 番号で行う。

- 各行の形式: `R<n> <パス:行（会話コメント由来はその旨を併記。抽出不能なら指摘の一行要旨のみ）>
  <指摘の一行要旨> / 修正報告: あり(要旨)・なし`。ゲート4で抽出した `パス:行` は会話コメント由来
  でも表示する（ユーザーが要旨だけで選別しなくて済むように）。
  `original_commit_id` が現在の `headRefOid` と一致する対象は行末に「head 未前進」と明示する
  （判定は新 head 基準なので実行はできるが、修正が入っていない事実を一覧で判別可能にする）。
- **修正報告の有無**は、行アンカーではスレッド内の返信（`in_reply_to_id` でぶら下がる他者の返信）
  から判定する。会話コメント由来の対象では、当該コメントより後の**認証ユーザー以外が投稿した**
  会話コメントのうち、本文が同一の `パス:行`（または当該指摘の内容）に言及するものを返信とみなす
  （自分の過去の検証返信を作者の修正報告として数えない）。報告は**作者の主張**として一覧に
  添えるのみで、解消の判定には使わない。
- **二重返信の防止**: 自分（認証ユーザー）の検証返信が既に付いている対象（行アンカーはスレッド内、
  会話コメント由来は上記と同じ言及基準で判定）は候補から外し、一覧に「検証返信済み
  （既存返信の URL）」として明示する（黙って減らさない。ユーザーの再検証指定で候補に戻せる）。
- deep-pr-review 由来でない自分のコメントが混じっている場合、ユーザーはこの一覧で除外を指示できる。

確定した対象が 0 件なら、worktree を作らずその旨を報告して終了する（後始末は不要）。

完了条件: 一覧を提示し、ユーザーが対象（除外・再検証指定を含む）を確定している。

## worktree の作成（コード参照）

新 head のコードを実体で読むため、使い捨ての worktree を作る。Claude Code の Bash は呼び出し
ごとに独立したシェルで変数を持ち越さないため、`mktemp -d` が出力した絶対パスをその場で応答本文に
控え、以降の `git -C`・サブエージェントへの受け渡し・後始末では、変数ではなくその絶対パスを
そのまま書く（以下の `<WT>` はこの絶対パスを指す）。

```sh
# BSD/GNU 両実装で通る template 形式（-t 形式は GNU mktemp で失敗する）
mktemp -d "${TMPDIR:-/tmp}/pr-recheck-wt.XXXXXX"   # 出力された絶対パス = <WT> を応答本文に控える
```

`<WT>` に上のブロックの出力（実際の絶対パス）を書き写してから実行する
（`<WT>` という文字列のまま実行しない）:

```sh
# pull/<番号>/head は同一リポPR・フォークPRの双方で解決できる。先頭の + は再実行時の強制更新に必須
git fetch <remote> "+pull/<PR番号>/head:refs/pr-recheck/<PR番号>"
git worktree add --detach <WT> "refs/pr-recheck/<PR番号>"
```

- 本節の `<remote>` は前提ゲート3の remote の突合で特定した remote を指す
  （既定名 `origin` を無条件に使わない）。
- **head の一致確認**（fetch の直後）: `git rev-parse refs/pr-recheck/<PR番号>` をゲート3の
  `headRefOid` と突合する。不一致なら（実行中に作者が push した等）`gh pr view <PR番号>
  --repo <owner>/<repo> --json headRefOid` で取り直し、以降はその新しい値を使う。取り直した
  head と ref の実体が一致しなければ再 fetch し、それでも一致しなければ検証を開始せず中止する
  （報告する SHA と実際に読むコードの食い違いを防ぐ）。
- 各コメントの検証用**範囲差分**は
  `git -C <WT> diff <original_commit_id>..<headRefOid> -- <パス>` で取る。
  `original_commit_id` が履歴に無ければ `git -C <WT> fetch <remote> <original_commit_id>` で
  取得を試みる。それでも取れない場合（force-push で旧 head が到達不能等）、範囲差分なし・
  新 head のコード実体のみで判定する（判定の定義は新 head 基準なのでそのまま成立する）。
  その旨を当該判定の根拠に明記する。
- worktree の作成に失敗したら、検証を開始せず失敗内容を報告して中止する
  （worktree なしの縮退検証はしない）。後始末は末尾の「報告と後始末」節を参照。

完了条件: worktree が `refs/pr-recheck/<PR番号>` から作成され、その絶対パス `<WT>` を応答本文に
控えている。

## 修正検証（判定）

確定した対象それぞれについて、**読み取り専用サブエージェント 1 体**で検証する
（Claude Code では Agent ツール・`subagent_type: general-purpose`。model は指定しない。
複数体は並列起動してよい。起動できない環境は「フォールバック規定」へ）。

サブエージェントのプロンプトに必ず含めるもの:

- コメント本文（指摘の全文）・`パス:行`（会話コメント由来はゲート4で抽出したもの。抽出できない
  場合は指摘の一行要旨）・`original_commit_id`（行アンカーのみ）・現在の `headRefOid`
- worktree の絶対パス `<WT>` と、「ファイル参照は `<WT>` 配下の絶対パス、git 操作は
  `git -C <WT>` で行い、作業ツリーのファイルとコミット履歴を変更しない（編集・書き込み・
  コミット禁止。範囲差分のための `git fetch` は例外として実行してよい）」の指示
- 範囲差分の取得コマンド（上記「worktree の作成」の形）。会話コメント由来は範囲差分を渡さず、
  新 head のコード実体のみで判定させる（その旨を根拠に明記させる）
- 判定の定義（逐語）:

  > 判定は二値である。**解消** = コメントが指摘した問題が、新 head のコードで再現しない
  > （指摘行の周辺実装まで読んで確認する。形だけ変わって問題が残る修正は未解消）。
  > **未解消** = それ以外。部分的な修正も未解消とし、何が残っているかの理由を必須で添える。

- 返却フォーマット（逐語）:

  ```
  R<n>: 解消 | 未解消
  根拠: <新 head のどのコード(パス:行)がどう変わった/変わっていないか。事実ベースで具体的に>
  残る問題: <未解消の場合のみ。何が残っているか>
  ```

完了条件: 全対象に二値判定と根拠が付いている。

## 判定レポートと選別

検証結果を一覧で提示する:
`R<n> [解消|未解消] <パス:行 または 会話コメント> <一行要旨> / 修正報告: あり・なし / <根拠の要約>`。

返信の**既定候補**は判定×修正報告の有無で組む:

- **解消**（報告の有無を問わず）→ 確認返信＋resolve の候補
- **報告あり・未解消** → 理由返信の候補
- **報告なし・未解消** → 候補にしない（まだ直っていないという催促の公開発信になるため、
  レポートで伝えるのみ。ユーザーが明示的に指示すれば候補に追加できる）

選別はユーザーが R 番号で確定する。**復唱と確認を経ない投稿は禁止**。候補全件を R 番号付きで
散文提示し、返信する R 番号のテキスト回答を待つ（切り捨てはしない）。前置きに、投稿先の PR 番号・
「選んだスレッドのみに返信する」こと・「解消判定のスレッドは返信後に resolve する（GitHub UI で
戻せる）」ことを含める。

1 件も選ばれなければ投稿せず、判定レポートのみで終了する（後始末は実行する）。

完了条件: 全 R の判定を提示し、返信する R 番号がユーザーのテキスト回答で確定している
（0 件の確定を含む）。

## publish-polish による返信整形

選ばれた各返信の文面を整形する。整形は前提ゲート2で Read した
`pr-comment/partial-application-contract.md`（publish-polish 部分適用契約の正本）の契約に
そのまま従う（本節では再掲しない）。

本スキルでの三点宣言（契約が求める想定読者・配布形態・約束するもの）:

- **想定読者**: PR の作者と、後からこのスレッドを読む第三者。
- **配布形態**: 対象リポジトリの PR レビュースレッドに残る返信。
- **約束するもの**: 検証の判定（解消 / 未解消）と、その根拠となる新 head の `パス:行` を示し、
  スレッドを閉じてよいか読者が判断できる材料を提供すること。

本スキル固有の適用要点:

- **内部語を落とす**: R 番号・判定機構への言及（サブエージェント・worktree・検証手順等）は
  読者の判断に寄与しないため、すべて落とす。
- **保護対象**: `パス:行`、識別子、数値、コミット SHA。
- **実体を変えない**の対象は、解消 / 未解消の判定・根拠・残る問題。
- 会話コメントへの返信は、冒頭で対象の指摘（`パス:行`。抽出できない場合は指摘の一行要旨）を
  明示する。

完了条件: 選ばれた全 R の返信文面が整形済みで、漏えい保留分はユーザーの判断
（修正して投稿 / 見送り）が確定している。

## 返信の投稿と resolve

**1 スレッド = 1 返信**で投稿する。複数の判定を 1 本にまとめない。

1件目を投稿する直前に `gh pr view <PR番号> --repo <owner>/<repo> --json headRefOid` を取り直し、
検証に使った head と一致することを確認する（不一致なら投稿を開始せず中止し、本スキルの再実行を
案内する — 選別の回答待ちの間に head が進んでいる場合があるため）。

行アンカーのレビューコメントへの返信:

```sh
gh api "repos/<owner>/<repo>/pulls/<PR番号>/comments/<コメントID>/replies" \
  -f body="$(cat <<'EOF'
<publish-polish 適用後の本文>
EOF
)" --jq '.html_url'
```

会話コメント由来の指摘への返信は、同じ heredoc 形式で
`gh pr comment <PR番号> --repo <owner>/<repo> --body "$(cat <<'EOF' … EOF
)"` を使う（デリミタのクォートで `$` や backtick のシェル展開を防ぐ）。

**解消返信を投稿したスレッドは resolve する**（未解消は返信のみで resolve しない）。
resolve は可逆であり（GitHub UI で unresolve 可能）、スレッド ID は GraphQL で引く:

```sh
# コメントID(databaseId) → スレッドID の対応を取得。hasNextPage が true の間、
# endCursor を -f cursor=<値> で渡して繰り返す（初回は cursor を渡さない）
gh api graphql -f query='query($owner:String!,$repo:String!,$pr:Int!,$cursor:String){
  repository(owner:$owner,name:$repo){pullRequest(number:$pr){
    reviewThreads(first:100, after:$cursor){pageInfo{hasNextPage endCursor}
      nodes{id isResolved comments(first:1){nodes{databaseId}}}}}}}' \
  -f owner=<owner> -f repo=<repo> -F pr=<PR番号>

gh api graphql -f query='mutation($id:ID!){
  resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -f id=<スレッドID>
```

会話コメントにはスレッド resolve が存在しないため、返信のみで完結する。

失敗時の挙動:

- **返信の投稿に失敗**（権限不足・認証切れ・レート制限・ネットワーク断など）したら、残りの返信を
  止める。それまでに投稿できた `html_url` と未投稿の R 番号を並べて報告し、原因と再開方法
  （原因の解消後に本スキルを再実行する — 投稿済み分は「検証返信済み」として自動的に候補から
  外れる）を添える。
- **スレッド ID が引けず resolve できない**場合（GraphQL の一覧に該当スレッドが無い等）は、
  返信のみで完結させ、resolve できなかった理由を報告に明記する（当て推量のスレッド ID で
  resolve しない）。
- **resolve の実行が失敗**した場合（権限不足・既に resolve 済み・レート制限等）は、その R の
  返信は投稿済みとして扱い、失敗理由を記録したうえで残りの R の処理を続ける（返信の投稿失敗と
  違い中断しない — 返信は既に公開済みで、resolve は GitHub UI からも実行できるため）。

完了条件: 選ばれた全 R について、返信の `html_url` と resolve の結果（`isResolved: true` /
resolve 不能の理由 / 会話コメント由来のため対象外）、または中断による未投稿の理由のいずれかが
記録されている。

---

## 報告と後始末

投稿した各返信の `html_url` を、R 番号・判定・対象の要約とともに一覧で報告する。あわせて、
返信 N 件（うち resolve M 件）/ 見送り K 件（検証返信済み・候補外の報告なし未解消・漏えい保留・
未選択の内訳）を明記する。

**後始末（正常終了・途中中止を問わず必須）**:

```sh
# <WT> は「worktree の作成」で応答本文に控えた絶対パス（変数は使わない）
git worktree remove --force <WT>
git update-ref -d refs/pr-recheck/<PR番号>
```

後始末の要否は操作単位で決める: `git fetch` を実行する前に中止した場合は後始末不要。fetch 後に
中止した場合は `git update-ref -d refs/pr-recheck/<PR番号>` を必ず実行し、worktree まで作成できて
いた場合はその前に `git worktree remove --force <WT>` を実行する。エラーでフローを中断する場合も、
中断を報告する前に実行する。

完了条件: 返信を投稿した場合は全返信の `html_url` と内訳が、投稿 0 件・中止の場合はその理由が
報告にある。加えて、fetch 済みなら `refs/pr-recheck/<PR番号>` が削除済みで、worktree を作成済み
なら `git worktree list` に `<WT>` が残っていない。

## フォールバック規定

サブエージェントを起動できない環境では、その旨を明記した上で、メイン側が対象を 1 件ずつ順次
検証する（判定の定義と返却フォーマットは同一。代替であることを報告に明記する）。
